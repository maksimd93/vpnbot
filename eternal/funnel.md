# Резервный вход при недоступности IP Eternal

31.10.2026 прямые подключения с домашнего Билайна к 146.103.110.71
не доходили до сервера: TCP 22/80/443 и UDP 44333/20000–20999.
С другой сети Hysteria успешно авторизовалась и передавала трафик;
ошибки сертификата, пароля и исходящего соединения не обнаружены.
Это наблюдение о маршруте, а не доказательство конкретного механизма блокировки.

Добавлен резервный VLESS XHTTP через Tailscale Funnel:

- Основной резерв: `https://vault.tail1bda7f.ts.net:443/ws050b63fe/`
  → `http://10.10.0.9:443/ws050b63fe/` (Xray).
- Прежний резерв: `https://vault.tail1bda7f.ts.net:10000` → `http://10.10.0.9:443`.
- XHTTP `packet-up`, TLS, прежние UUID и правила отключения пользователей.
- Ссылка и QR: VLESS → пользователь → «Резервное подключение».
- На телефоне нужен только совместимый VPN-клиент; приложение Tailscale не требуется.
- В LxBox в настройках резервного узла → TLS необходимо явно выключить
  «SNI в смешанном регистре» и «Разбивать рукопожатие на TLS-записи».
  Не оставлять наследование включённых глобальных параметров. Затем переподключиться.
- Настройка `pac.json`: `eternal_funnel = {enabled: true, host: "vault.tail1bda7f.ts.net", port: 443}`.
- `tailscale funnel --bg` сохраняет вход после перезапуска. Адрес Xray закреплён в Docker Compose.
- Корневой маршрут Funnel 443 (VaultWarden) и весь 8443 (API-роутер) сохраняются.
- Это резерв для TCP/HTTPS-транспорта VLESS. Прямую Hysteria/AmneziaWG на недоступном IP он не восстанавливает.
- Funnel имеет ограничения пропускной способности: https://tailscale.com/docs/features/tailscale-funnel

Проверка с ПК через физический Wi-Fi, без использования работающего стороннего VPN:
выходной IP 146.103.110.71; HTTPS скачал 10 000 000 байт за 6,2 с (~13 Мбит/с).

Повторная диагностика 31.10 около 07:55 МСК после отказа на телефоне:
проверено ядром sing-box-lx v1.14.4-lx.25 (официальный Windows-релиз,
SHA256 сверена с SHA256SUMS). Базовый профиль, с явным Host и с ALPN h2
успешно выполняют HTTPS-запрос через физический Wi-Fi. Смешанный регистр SNI
и `tls.record_fragment=true`, включённые по отдельности, воспроизводимо
обрывают соединение до авторизации в Xray. Это подтверждённые несовместимости;
Макс подтвердил: после отключения этих двух параметров на телефоне Wi-Fi работает хорошо.

У LxBox параметры TLS наследуются от общих настроек. Поэтому первоначальный
успешный тест через Xray не покрывал пользовательскую конфигурацию LxBox.
Импорт другой VLESS-ссылки сам по себе не отменяет это наследование.

## Резерв 443 и мобильная сеть

После подтверждения Wi-Fi Макс сообщил о проблемах на LTE. Добавлен параллельный
вход на стандартном HTTPS-порту 443, чтобы проверить доступ без зависимости от
порта 10000. Блокировка 10000 оператором пока не доказана; доступа к LTE с этого
ПК нет. Работа нового профиля на LTE требует проверки на телефоне.

Новая ссылка в боте называется «резерв 443»; старые импортированные ссылки сами
не меняются. QR селектор 4 выдаёт основной профиль, 5 — прежний резерв 10000.
На новом узле снова явно отключить обе несовместимые настройки TLS.

У профиля 443 заданы Host и ALPN `h2`, режим остаётся `packet-up`. В `extra.xmux`:

```json
{"maxConnections":3,"hMaxRequestTimes":"600-900","hMaxReusableSecs":"180-300","hKeepAlivePeriod":15}
```

Проверка простаивающего HTTP/2-соединения начинается через 15 вместо 45 секунд.
Соединения перестают выбираться для новых потоков через 180–300 секунд;
активные потоки при этом не закрываются. Лимиты пула и числа запросов сохранены:
явный объект XMUX заменяет, а не дополняет значения по умолчанию ядра.
Это настройка восстановления соединений, а не доказанное устранение проблемы LTE.

Настройки сверены с исходниками официального sing-box-lx v1.14.4-lx.25:
`transport/v2rayxhttp/http2.go`, `xmux.go`; импорт `extra` — с парсером LxBox
`app/lib/services/parser/transport.dart`. Само приложение телефона удалённо
не проверено. Серверные транспорт, UUID, пароли и параметры других протоколов
не менялись.

Проверка 31.10 около 15:42 МСК с физического Wi-Fi ядром LxBox: выходной IP
Eternal, 12 из 12 последовательных HTTPS-запросов успешны, загрузка 10 МБ за
3,95 с, отправка 1 МБ за 0,79 с. После 50 секунд простоя следующий запрос
успешен за 0,35 с; ошибок ядра в этом прогоне нет. Проверка не моделирует LTE
и не доказывает восстановление после смены сети. Первый предварительный прогон
443 без окончательного профиля имел таймаут 8 секунд во время холодного DNS;
повторная загрузка прошла. Для итогового прогона таймаут соединения — 15 секунд.

## Восстановление маршрута Funnel

Убедиться, что адрес Xray не изменился:

```sh
docker inspect xray-2.29 --format '{{with index .NetworkSettings.Networks "vpnbot_default"}}{{.IPAddress}}{{end}}'
tailscale funnel --bg --https=10000 http://10.10.0.9:443
tailscale funnel --bg --https=443 --set-path=/ws050b63fe/ http://10.10.0.9:443/ws050b63fe/
tailscale funnel status
```

Для 443 путь должен совпадать с текущим `xhttpSettings.path` в Xray. Funnel
убирает префикс точки монтирования перед проксированием; поэтому тот же путь
обязательно включён в URL целевого сервиса. Корневой обработчик `/` не менять.

Для восстановления прямой Hysteria нужен доступный маршрут к исходному IP либо
дополнительный IPv4 в кабинете VDSina. Перед переносом проверить новый адрес из
нужных сетей; доступность нового IP заранее не гарантируется. Сначала добавить
адрес параллельно, не заменять старый и не перевыпускать все ключи.

## Откат

Откат только нового входа 443: вернуть `eternal_funnel.port=10000`, затем:

```sh
tailscale funnel --https=443 --set-path=/ws050b63fe/ off
```

Не отключать весь Funnel 443: там работает VaultWarden. Копии настроек до
добавления пути: `/root/vpnbot-backups/20261031-funnel443/`.

Отключение прежнего входа 10000:

```sh
tailscale funnel --https=10000 off
```

Затем отключить `eternal_funnel.enabled` в `config/pac.json`.
Не использовать `tailscale funnel reset`: это затронет остальные сервисы.
Исходная конфигурация Funnel и копии изменённых файлов сохранены вне git
в `/root/vpn-diagnostics-20261031/` и `/root/vpnbot-backups/20261031-funnel/`.
